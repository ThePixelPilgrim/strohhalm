# Strohhalm — sync activity log

**Date:** 2026-09-06
**Status:** approved, awaiting a plan
**Builds on:** `2026-07-25-strohhalm-design.md` (storage, runner, UI shape) and
`2026-07-26-sha256-mirror-engine-design.md` (the engine that measures the pack).

## Purpose

The app records only each repository's *latest* outcome. Once the scheduled
sync runs unattended, that is not enough: a run at 02:00 that received data and
a clean run at 03:00 leave the row looking as if nothing happened overnight.

This adds a log of sync attempts, one entry per repository per attempt, and a
screen that shows it. The screen opens filtered to the entries that actually
received data, because that is the question the user asks: *which mirrors moved,
and by how much?*

### Success criteria

- Every sync attempt, manual or scheduled, produces exactly one entry with the
  repository, start and end time, outcome, bytes received, refs changed, and
  the trigger.
- "Bytes received" is the size of the pack the server sent, and is exactly
  zero when the engine skipped the fetch because nothing moved upstream.
- The Activity screen opens showing only entries that received data, and one
  toggle reveals everything else.
- Entries older than 30 days are gone without user action.
- A repository that is renamed or deleted keeps its past entries legible.

## Why not the alternatives

**A text log file in internal storage.** No migration, trivial to append. But the
filter means parsing lines, the screen would re-read the file on every open,
and a 30-day prune is a rewrite of the file. The app already has Room; a second
persistence layer for the same kind of data is the wrong trade.

**"Last bytes received" on the repository row.** No new table. But it is not a
log: it shows one number per repository, and the overnight case above is
exactly what it cannot answer.

**Recording only entries that received data.** The smallest table. Rejected
because failures during a scheduled run are the other thing the user cannot see
while asleep; they would be recorded nowhere except as the row's latest state,
which the next clean run overwrites.

## Scope

In: the entity and DAO, the engine reporting two extra numbers, the runner
writing entries, the Activity screen with its filter, retention, tests.

Out: a per-repository history on the detail screen, exporting the log, and any
event that is not a sync attempt (key regeneration, folder changes, host-key
confirmations). Each is a later spec if wanted.

## Architecture

### Data

A new Room entity `SyncEvent` in table `sync_events`:

| column | type | meaning |
| --- | --- | --- |
| `id` | Long, autogenerated | primary key |
| `repoId` | Long | the `repos.id` at the time; not a foreign key, so deletion of the repo leaves the entry |
| `repoName` | String | `displayName` copied at write time, so a rename or deletion does not blank the entry |
| `startedAt` | Long | epoch millis when this repository's sync began |
| `finishedAt` | Long | epoch millis when it ended, however it ended |
| `outcome` | `SyncEventOutcome` | `RECEIVED`, `UP_TO_DATE`, `FAILED`, `CANCELLED` |
| `bytesReceived` | Long | pack transfer size; 0 unless `RECEIVED` |
| `refsChanged` | Int | refs whose target differs from before the sync; 0 unless `RECEIVED` |
| `errorCode` | String? | `SyncErrorCode.name` when `FAILED`, else null |
| `trigger` | `SyncTrigger` | `MANUAL` or `SCHEDULED` |

Both enums get a `TypeConverter` beside `SyncStatusConverter`, with the same
fall-back-on-unknown behaviour. An index on `startedAt` serves the screen's
ordering and the prune.

The database goes from version 1 to 2 with a Room `@AutoMigration(from = 1,
to = 2)`. Adding a table is within what auto-migration handles; the exported
schema for version 2 lands in `app/schemas/`.

`SyncEventDao`:

- `observeRecent(since: Long, receivedOnly: Boolean): Flow<List<SyncEvent>>`,
  newest first. `receivedOnly` maps to `outcome = 'RECEIVED'`.
- `insert(event: SyncEvent)`
- `deleteOlderThan(cutoff: Long)`
- `recordAndPrune(event: SyncEvent, cutoff: Long)`, a `@Transaction` default
  method that calls the two above, so the DAO alone gives atomicity and the
  log needs no handle on the database.

`DefaultSyncLog` in `domain` implements the `SyncLog` interface below over the
DAO. Its `record` calls `recordAndPrune` with a cutoff 30 days before the
event's own `finishedAt`. The prune runs on every insert because it is one
indexed `DELETE`, and doing it here means there is no separate maintenance path
to forget.

### Engine

`MirrorOutcome.Success` gains two fields with defaults:

```kotlin
data class Success(
    val sizeBytes: Long,
    val refCount: Int,
    val bytesReceived: Long = 0,
    val refsChanged: Int = 0,
) : MirrorOutcome
```

`ProtocolMirror` fills them on the path that fetches: `bytesReceived` is
`PackResult.bytes`, which `KotlinPackIndexer` already computes and the mirror
currently discards. `refsChanged` is the number of names in the new ref list
whose target differs from `mirror.localRefs()` read before `writeRefs`, plus
names that are new. The empty-remote and up-to-date paths report zero for both.
`JGitMirror` keeps its existing call and takes the defaults; it is unused and
gated on hardware checks, and this spec does not touch it.

The rule that only `ProtocolMirror` and `JGitMirror` know git stands. Nothing
above the `GitMirror` interface learns what a pack is.

### Recording

In `domain`:

```kotlin
enum class SyncTrigger { MANUAL, SCHEDULED }

interface SyncLog {
    suspend fun record(event: SyncEvent)
}

object NoSyncLog : SyncLog   // tests, and the default
```

`SyncRunner` gains `log: SyncLog = NoSyncLog` and its two launch methods gain
`trigger: SyncTrigger = SyncTrigger.MANUAL`. `ScheduledSync` passes
`SyncTrigger.SCHEDULED`. Existing callers and tests compile unchanged.

Inside `sync(repo)`, the event is written immediately after the row update it
corresponds to, so the two cannot disagree:

- `MirrorOutcome.Success` with `bytesReceived > 0` → `RECEIVED`
- `MirrorOutcome.Success` with `bytesReceived == 0` → `UP_TO_DATE`
- `MirrorOutcome.Failure` → `FAILED` with the error code
- `CancellationException` → `CANCELLED`, written under `NonCancellable` in the
  same block that already marks the row, then rethrown as today

`AppContainer` builds `DefaultSyncLog` over the new DAO and passes it to the
runner. It is the only wiring change.

### Screen

`ActivityScreen` at route `Routes.ACTIVITY = "activity"`, reached from a
history icon in the repo list's top bar, between Sync now and Settings. Back
returns to the list.

`ActivityViewModel` holds `receivedOnly: StateFlow<Boolean>`, initially true,
and `events: StateFlow<List<SyncEvent>>` from
`observeRecent(now - 30 days, receivedOnly)` re-collected when the toggle
changes. The 30-day bound on the query is belt and braces against entries the
prune has not reached yet; the prune is the real retention.

Layout, top to bottom:

- A `FilterChip` labelled "Received data only", selected by default.
- A `LazyColumn`, newest first. Each row shows the repository name, a relative
  time from the existing `relative()` helper, and one line of details:
  - `RECEIVED`: bytes via `Formatter.formatShortFileSize`, refs changed,
    duration
  - `UP_TO_DATE`: "Up to date", duration
  - `FAILED`: the message from `syncErrorText`, duration
  - `CANCELLED`: "Stopped", duration
  A small trailing label reads "scheduled" or "manual".
- Empty states: with the filter on, "No sync has received data in the last 30
  days"; with it off, "No syncs in the last 30 days".

All text goes through `strings.xml`. Durations are rendered as seconds under a
minute, else minutes and seconds.

## Error handling

Writing an event must never fail a sync. `SyncRunner` wraps `log.record` in
`runCatching`; a lost log entry is a lesser fault than a mirror marked failed
because its bookkeeping threw.

An unknown `outcome` or `trigger` string read back from the database falls back
to `FAILED` and `MANUAL` respectively, as the settings and status converters
already do for their enums, so a downgrade cannot crash the screen.

## Testing

JVM, following the existing fake-DAO pattern:

- `SyncRunnerLogTest`: one event per attempt; outcome, bytes, refs and trigger
  match the mirror's outcome; a cancelled sync records `CANCELLED`; a throwing
  log does not change the row's status.
- `ScheduledSyncTest` gains a case: the scheduled cycle records `SCHEDULED`.
- `DefaultSyncLogTest` over a `FakeSyncEventDao`: insert then prune removes
  entries older than 30 days from the event's `finishedAt` and keeps newer ones.
- `MirrorEndToEndTest` gains assertions: the first sync over the local SSH
  server reports `bytesReceived > 0` and `refsChanged` equal to the ref count;
  an immediate second sync reports both as zero.
- `ActivityViewModelTest`: the filter toggle changes which entries are exposed.

Instrumented, written but unrun until a device is attached, as with the rest of
`androidTest`: a `MigrationTestHelper` test that opens a version-1 database and
migrates it to 2.

## Accepted risks

- **Auto-migration must be validated on a device.** The instrumented test
  exists for this; until it runs, the migration is only checked by Room's
  compile-time schema diff.
- **Bytes received is transfer size, not disk growth.** The user chose this. The
  mirror folder can grow by more than the pack (the `.idx` is written beside it)
  or shrink later; the log does not try to reconcile the two.
- **A sync interrupted by process death leaves no entry.** The row is reset to
  `INTERRUPTED` on the next start by `resetStale`; the log stays silent because
  the runner that would have written the entry is gone. Recording an
  `INTERRUPTED` event from `resetStale` is a possible follow-up, not part of
  this spec.
